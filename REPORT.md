# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме (Executive Summary)

В рамках лабораторной работы спроектирован процесс разработки нового
микросервиса «Расчет корзины и скидок» для системы лояльности.

Цель проекта: выбрать технологию хранения данных, настроить репозиторий и
командные стандарты, внедрить автоматический контроль качества кода,
проанализировать legacy-код и подготовить план его ревью.

Основные результаты:

- выбрана СУБД PostgreSQL по результатам взвешенного сравнения с MongoDB
  (4.30 против 3.90);
- настроен репозиторий с моделью ветвления `main` / `develop` / `feature/*`,
  файлами `.editorconfig` и `CODEOWNERS`, защитой ветки `develop`;
- настроен CI на GitHub Actions с запуском flake8 для каждого Pull Request;
  работа Quality Gate проверена методом «сломать и починить»;
- построена UML-диаграмма деятельности для функции `calculate_cart_total`,
  выявлены запахи кода, подготовлен план code-review.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений

| Критерий | Вес | PostgreSQL | MongoDB |
|---|---|---|---|
| ACID-транзакции и целостность данных | 0.35 | 5 | 3 |
| Производительность чтения и аналитических запросов | 0.20 | 4 | 4 |
| Гибкость схемы | 0.10 | 3 | 5 |
| Горизонтальная масштабируемость | 0.15 | 3 | 5 |
| Стоимость владения и экосистема | 0.20 | 5 | 4 |
| **Сумма весов** | **1.00** | | |

Оценки выставлены по 5-балльной шкале.

### 2.2. Расчет и обоснование выбора

Формула взвешенной оценки:

```
Оценка = Σ (Вес_критерия × Балл_кандидата)
```

**PostgreSQL:**
0.35·5 + 0.20·4 + 0.10·3 + 0.15·3 + 0.20·5 = 1.75 + 0.80 + 0.30 + 0.45 + 1.00 = **4.30**

**MongoDB:**
0.35·3 + 0.20·4 + 0.10·5 + 0.15·5 + 0.20·4 = 1.05 + 0.80 + 0.50 + 0.75 + 0.80 = **3.90**

Обоснование весов:

- **ACID (0.35)** имеет максимальный вес: сервис хранит баллы и транзакции,
  ошибка в таких данных (двойное списание, потеря баллов) недопустима.
  PostgreSQL обеспечивает полноценные транзакции «из коробки». В MongoDB
  многодокументные транзакции есть, но они сложнее и дороже по
  производительности.
- **Производительность чтения (0.20)** важна для истории операций и отчетов.
  Простые выборки быстры в обеих СУБД, сложные отчеты с JOIN удобнее
  в PostgreSQL, поэтому оценки равны.
- **Стоимость и экосистема (0.20):** обе СУБД бесплатны в базовом варианте,
  но у PostgreSQL выше зрелость и богаче инструменты для финансовой
  отчетности.
- **Масштабируемость (0.15):** у MongoDB шардинг встроенный, PostgreSQL
  масштабируется сложнее, но для стартапа на старте этого достаточно.
- **Гибкость схемы (0.10)** имеет минимальный вес: структура транзакций
  строгая и меняется редко. Для редких гибких полей в PostgreSQL есть JSONB.

**Вывод:** побеждает PostgreSQL (4.30 против 3.90). Решающий вклад дает
критерий ACID. Преимущество MongoDB в гибкости и масштабируемости не
компенсирует слабость в обеспечении целостности финансовых данных.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма

UML-диаграмма деятельности функции `calculate_cart_total`:

![UML Diagram](https://raw.githubusercontent.com/vipix2/lab1-comprehensive-Biryulin/feature/review-plan/docs/uml_diagram.png)

Файл диаграммы: [docs/uml_diagram.png](https://github.com/vipix2/lab1-comprehensive-Biryulin/blob/feature/review-plan/docs/uml_diagram.png)
(находится в ветке `feature/review-plan`, Pull Request с которой оставлен
открытым).

Выявленные запахи кода (Code Smells) в legacy-фрагменте:

1. **Магические числа:** `15000`, `0.85`, `500`, `0.90`, `0.97`, `0.93`,
   `0.70` не имеют имен и смысла в коде.
2. **Магические строки:** промокоды `"SUMMER"` и `"VIP"` зашиты в логику.
3. **Непонятные уровни лояльности:** `tier == 1` и `tier == 2` без
   пояснения, что они означают.
4. **Нет валидации входных данных:** возможны отрицательная `cart_sum`,
   неизвестный `tier`, `promos=None`.
5. **Порядок применения скидок зависит от порядка промокодов:** `-500`
   и `* 0.90` дают разный итог при разной очередности.
6. **Фиксированная скидка `-500` может привести цену к отрицательному
   значению** до проверки нижней границы.
7. **Нет защиты от повторных промокодов:** `["SUMMER", "SUMMER"]`
   применит скидку дважды.
8. **Цепочки `if/elif` вместо таблицы правил:** для нового промокода или
   уровня нужно править функцию.
9. **Функция делает все сразу:** базовая скидка, промокоды, лояльность
   и ограничение смешаны в одном месте.
10. **Нет округления:** денежные суммы считаются дробными числами,
    возможны погрешности.
11. **Нет документации и аннотаций типов.**

### 5.2. План code-review

Подход: ревью модуля `src/discount.py` проводится через Pull Request
по заранее согласованному плану с целями, измеримыми критериями, ролями
участников и процедурой эскалации.

Открытый Pull Request с файлом `docs/review-plan.md`:
https://github.com/vipix2/lab1-comprehensive-Biryulin/pull/3

Ключевые измеримые критерии:

- в коде нет магических чисел (константы вынесены и названы);
- входные данные валидируются;
- покрытие тестами модуля больше 80%;
- flake8 проходит без замечаний;
- итоговая скидка не превышает 30% от суммы корзины.

Механизм эскалации: спор обсуждается автором и ревьюером в комментариях
к Pull Request; если согласия нет за 1 рабочий день, решение принимает
Tech Lead и фиксирует его в комментарии; споры о бизнес-правилах скидок
решает владелец продукта.

## 6. Заключение

Настроенные процессы снижают риск внесения дефектов на нескольких уровнях.
Защита ветки `develop` и обязательные Pull Request исключают прямые правки
в базовую ветку. `CODEOWNERS` закрепляет ответственность за код. Автоматический
линтер в CI отсеивает типовые ошибки до слияния, что подтвердил эксперимент
«сломать и починить»: красный статус не давал сливать код с нарушениями.
Анализ legacy-кода и план ревью с измеримыми критериями позволяют находить
логические ошибки и риски (фрод, некорректные скидки), которые линтер
не обнаруживает. Обоснованный выбор СУБД с упором на ACID снижает риск
потери и искажения финансовых данных.
